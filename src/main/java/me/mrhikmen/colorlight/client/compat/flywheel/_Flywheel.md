# Flywheel

**What it does:** with the GPU pipeline (Sodium) on, everything Flywheel draws (instanced block entities and entities, Create contraptions, Vanillin) is lit per pixel by ColorLight's coloured light, like the terrain. Without Flywheel nothing changes; without the GPU pipeline Flywheel keeps its own light.

**How it works:**
- Flywheel builds its fragment shaders from text (`assets/<ns>/flywheel/...`). `SourceFileMixin` (`colorlight.mixins.json`) patches the text of every light shader (anything defining `flw_shaderLight`) and of `internal/common.frag` as Flywheel parses it. The light shader keeps its own code (renamed `_cl_flwOrigLight`) and a wrapper runs it, then `cl_flwApply()` from `assets/colorlight/flywheel/colorlight/flw.glsl`; `common.frag` multiplies by the result instead of the lightmap lookup.
- `cl_flwApply()` reads the same light volume as the terrain shader. `flw_vertexPos` is relative to `flw_renderOrigin`, so the position relative to the camera block is `flw_vertexPos + (renderOrigin - cameraBlock)`; the normal comes from screen-space derivatives. Flywheel's own sky light (smooth / embedded) is kept; its block light is replaced by the volume; an instance with block light 15 (full-bright) stays full-bright.
- The world volume's buffers sit on texture units 10..12 (Flywheel uses 0..9) while the engine draws (`EngineImplMixin`, around `render` / `renderCrumbling`). `ContextShaderMixin` points the samplers at them when a program is linked.
- Whether ColorLight is used is the volume header's enabled flag, read in the shader: config switch, shader packs and failures need no recompile, and the shader falls back to Flywheel's light. While no volume exists an all-zero one is bound.
- **Sable sub-levels.** Sable draws block entities / Create contraptions of a sub-level in a Flywheel embedding with a *lighting scene id* (its own copies of the light shaders read `flw_vertexLightingSceneId` / `flw_vertexLightingPos`, the vertex in scene coordinates = plot space minus the plot's centre chunk corner). `SableFlywheelScenes` publishes per scene id the sub-level's `SableLightVolume` window (anchor, first page, plot offset) in a small buffer (`u_CLScenes`, unit 13); the sub-level volume's data / pool go to units 14 / 15. `flw_apply_sable.glsl` (chosen when the light shader mentions the scene id) reads that window the same way the Sable terrain shaders do. Windows are acquired for sub-levels within 160 blocks.
- Mixins live in `cmixin.*`, not under `compat.*`: Sinytra Connector (NeoForge) refuses to load classes from a package that a mixin config owns.
- Nothing is compiled against Flywheel; every mixin is `@Pseudo` with `require = 0`.

**Light of Flywheel objects** (`compat/create/CreateContraptionLightLinker`, option "Light of contraptions", `CREATE_CONTRAPTION_LIGHT`, shown with Create): the blocks of a Create contraption are not in the level, so ColorLight never saw their light sources. Every light-emitting block of a nearby contraption (strongest 24, rescanned when its block count changes and every 40 ticks) becomes a dynamic light that follows the contraption (`toGlobalVector`, updated in 1/4-block steps, floods per tick capped separately for the contraption's own space, the world and other sub-levels, new links first, lights visited in a rotating order so a fast ship cannot starve the later lights, same worker design as `SableLightLinker`). A contraption counts as being on a sub-level when it is within 24 blocks of the plot's block box (pistons / carriages stick out of it). It lights the terrain and, through the shared volume, the contraption's own Flywheel objects. A contraption inside a Sable sub-level is lit in plot space (the ship's objects) and in world space (the terrain). Lights of ordinary block entities and of blocks placed on a ship are static sources and already work. Create is read by reflection.

**Limitations:** the volume covers 31 sections around the camera horizontally (15 vertically), farther away Flywheel objects get no coloured block light. Sub-level objects use the sub-level window (31 sections around the middle of its bounding box, at most 16 sub-levels). The CPU (vertex colour) pipeline does not light Flywheel objects. Written against Flywheel 1.0.7 / Minecraft 1.21.1; not compiled or run (no network in the authoring environment) - please test.

**Что это делает:** При включенном конвейере GPU (Sodium) всё, что рисует Flywheel (экземпляры блочных сущностей и сущностей, создаваемые механизмы, Vanillin), освещается попиксельно цветным светом ColorLight, как и ландшафт. Без Flywheel ничего не меняется; без конвейера GPU Flywheel сохраняет собственное освещение.

**Как это работает:**
- Flywheel создаёт свои фрагментные шейдеры из текста (`assets/<ns>/flywheel/...`). `SourceFileMixin` (`colorlight.mixins.json`) вносит изменения в текст каждого шейдера освещения (всё, что определяет `flw_shaderLight`) и в `internal/common.frag` по мере того, как Flywheel его анализирует. Шейдер освещения сохраняет свой собственный код (переименованный в `_cl_flwOrigLight`), и его запускает обертка, затем `cl_flwApply()` из `assets/colorlight/flywheel/colorlight/flw.glsl`; `common.frag` умножает результат вместо поиска по карте освещения.

— `cl_flwApply()` считывает тот же объем освещения, что и шейдер ландшафта. `flw_vertexPos` относительно `flw_renderOrigin`, поэтому позиция относительно блока камеры равна `flw_vertexPos + (renderOrigin - cameraBlock)`; нормаль берется из производных экранного пространства. Собственный источник света неба Flywheel (smooth / embedded) сохраняется; его блочный свет заменяется объемом; экземпляр с блочным светом 15 (полная яркость) остается полностью ярким.

- Буферы мирового объема располагаются на текстурных блоках 10–12 (Flywheel использует 0–9), в то время как движок отрисовывает (`EngineImplMixin`, примерно в области `render` / `renderCrumbling`). `ContextShaderMixin` направляет сэмплеры на них при компоновке программы.

- Использование ColorLight определяется флагом enabled заголовка объема, который считывается в шейдере: переключатель конфигурации, пакеты шейдеров и ошибки не требуют перекомпиляции, и шейдер возвращается к освещению Flywheel. Пока объем отсутствует, привязан нулевой объем.

- **Подуровней Sable.** Sable отрисовывает блочные сущности / Создает конструкции подуровней во встраивании Flywheel с *идентификатором сцены освещения* (собственные копии шейдеров освещения считывают `flw_vertexLightingSceneId` / `flw_vertexLightingPos`, вершина в координатах сцены = пространство участка минус угол центрального блока участка). `SableFlywheelScenes` публикует для каждого идентификатора сцены окно `SableLightVolume` подуровней (якорь, первая страница, смещение участка) в небольшой буфер (`u_CLScenes`, блок 13); данные/пул объема подуровней попадают в блоки 14/15. `flw_apply_sable.glsl` (выбирается, когда шейдер освещения указывает идентификатор сцены) считывает это окно так же, как и шейдеры ландшафта Sable. Окна захватываются для подуровней в пределах 160 блоков.

- Миксины находятся в `cmixin.*`, а не в `compat.*`: Sinytra Connector (NeoForge) отказывается загружать классы из пакета, принадлежащего конфигурации миксина.

- Ничто не компилируется с Flywheel; каждый миксин имеет `@Pseudo` с `require = 0`.

**Объекты Light of Flywheel** (`compat/create/CreateContraptionLightLinker`, опция "Light of contraptions", `CREATE_CONTRAPTION_LIGHT`, отображается с Create): блоки механизма Create находятся вне уровня, поэтому ColorLight никогда не видел их источников света. Каждый излучающий блок расположенного рядом механизма (24 самых мощных, повторно сканируются при изменении количества блоков и каждые 40 тактов) становится динамическим источником света, который следует за механизмом («toGlobalVector», обновляется с шагом в 1/4 блока, количество затоплений в такт ограничено отдельно для собственного пространства механизма, мира и других подуровней, сначала новые связи, источники света посещаются в порядке ротации, чтобы быстрый корабль не мог лишить последующих источников света, та же конструкция рабочих, что и у «SableLightLinker»). Механизм считается находящимся на подуровне, когда он находится в пределах 24 блоков от блочного ящика участка (поршни/кареты выступают из него). Он освещает местность и, через общий объем, собственные объекты Flywheel механизма. Механизм внутри подуровня Sable освещается в пространстве участка (объекты корабля) и в мировом пространстве (местность). Источники света обычных блоков и блоков, размещенных на корабле, являются статическими источниками и уже работают. Созданный объект считывается с помощью отражения.

**Ограничения:** объем охватывает 31 секцию вокруг камеры по горизонтали (15 по вертикали), на большем расстоянии объекты Flywheel не получают цветного блочного освещения. Объекты подуровней используют окно подуровней (31 секция вокруг середины ограничивающего параллелепипеда, максимум 16 подуровней). Конвейер ЦП (цвет вершин) не освещает объекты Flywheel. Написано для Flywheel 1.0.7 / Minecraft 1.21.1; не скомпилировано и не запущено (нет сети в среде разработки) — пожалуйста, протестируйте.
